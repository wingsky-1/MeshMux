# 11d Hub 自升级执行 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 Hub 自己能升级：预升级 DB 备份（扁平记录）→ root 预置目标 manifest → 已校验 staged 包 → 协调换 Hub 二进制与 co-located Line 四处 pin → 重启 → 启动身份回读确认；失败可恢复（restore 唯一路径）。

**Architecture:** 记录层抽到中立叶子包 `internal/backup`（唯一编码器，per-op / flat 两种布局）；版本身份唯一来源 `internal/buildinfo`；执行面是 root 属主静态 oneshot + path unit（Web 只写 `/run` 请求文件，无特权调用）；op journal 是权威、`hub_upgrade_operations` 是 schema 11 镜像；`confirmed` 只由 running `version+digest` 判定；恢复走旧包的 `__internal-hub-restore` + 新 data-dir + drop-in 翻 `--data-dir`。

**Tech Stack:** Go 1.27.2, stdlib; `modernc.org/sqlite`（仅 Web/Hub 侧，VACUUM/`integrity_check`）；`node.CommandRunner` 固定 argv；systemd 静态 oneshot + `.path` + tmpfiles；既有 `install.ReadState` / `nodeManagedFiles` 编码语义。

**Spec:** `docs/superpowers/specs/2026-10-26-11d-hub-self-upgrade-design.md`（分支 `feat/11d-design`，第 4 稿，内部评审通过）— 执行者必须同时读 spec 与本文；spec 是语义权威，本文只做任务切分与文件/接口裁定。

**Task 顺序说明：** 本文是 7 个任务而非 ~6。`buildinfo` 前移到 Task 2（producer 的 `from_version`/`from_package_sha256`/`from_agent_sha256` 只能来自它，不能来自 `os.Executable()` 或常量）；dispatch 基座（Task 4）与 handoff/journal 镜像/对账（Task 5）拆开，因为前者是 R-SURFACE 特权面审查、后者是状态机审查，合并后单个 PR 无法独立验收。其余顺序与 spec §5.2 → §5.7 一致。

- 不新增 protocol kind：`upgrade.*` / `rollback.*` 继续拒绝（`internal/protocol/protocol.go:322`）；不新增公开 HTTP 写面，Hub 三个写路由都走既有 `app.mutation`。

- 秘密边界：payload 0700/0600 `meshmux`，记录 metadata-only；日志/回执不记 token、订阅 URL、DB 内容；只有 `SCHEMA_TOO_NEW` 记 detail（记录路径）。result 0640 `root:meshmux`，ledger 保持 0600 root，Web 无 ledger 读权。

- 测试只做 B 级 fixture：不触碰宿主 systemd、不装包、不改现网；C 级隔离 VM/真机归 #12，任何任务不得声称端到端可用。
- 12e 拥有发布通道：在 `meshmuxd` 从 `file://` dev pin 切到真实 release asset 之前，生产 Hub 的目标 manifest 只会得到 `MANIFEST_UNAVAILABLE`；B 级 fixture 只证形状，不得据此声称 Web 统一升级可用。

## Review Focus

1. **跨 uid 属主**：root dispatcher 以 `expectedOwner=meshmux` 读 0600 记录/载荷，Web 不能读 root ledger，result 在 Web data-dir 之外且 Web 不可写 —— `TestDispatchReadsMeshmuxOwnedRecord`、`TestResultDirRejectsWebWrites`（Task 4）；`TestExpectedOwnerEnforced`（Task 1）。
2. **TOCTOU staged 换字节**：按 fd 校验后不能按路径 exec；必须复制到 root-only `exec-<op>` 再 exec，校验后被替换不影响已复制字节 —— `TestDispatchExecsVerifiedCopy`（Task 4）。
3. **Line 第 4 个 pin 漂移**：只重钉 Hub ledger / Line ledger `shared_binaries` / `agent.json`、漏 Line ledger `state.Node` 会让下一次 `--from-recorded-state` 报 `CONFIG_CONFLICT` —— `TestLineRepinFourthPinNeeded`（Task 6）；四处写全成或全败 `TestLineRepinAllOrNothing`（Task 6）。
4. **GC 吃掉 failed/staged 回退源**：候选集只有 `confirmed`；确认前任何路径不得回收；`staged` 是合法 restore 源；Hub 的 flat 单槽布局下 GC 恒 no-op，新备份原子替换而非先删 —— `TestGCOnlyConfirmedGenerations`、`TestGCFlatKeepsOneGeneration`（Task 1）、`TestBackupNeverCollectsBeforeConfirm`（Task 3）、`TestConfirmNeverCollectsFlatSource`（Task 5）、`TestRestoreAcceptsStagedSource`（Task 7）。
5. **健康路径写入**：`/healthz` 只 `SELECT 1`，身份不匹配/行缺失/`user_version` 异常都不改 200/503 且零写；回读只消费 `database_versions`，不重写 —— `TestHealthzSelectOneOnly`、`TestReadbackNeverWrites`（Task 2）。

## 与 spec 的三处已知缺口（本计划的裁定）+ 一处设计决定

1. **`/var/lib/meshmux-installer` 的 0700 与 §5.9 的可读性冲突**。今天该目录是 `root:root 0700`（`internal/install/apply.go:32` + `apply.go:331` 的 `ensureDirectory(..., 0700)`），而 §5.9 要求 Web 读 `hub-upgrade/results/`（`root:meshmux 0750`）并解析 `upgrade/manifest-*.json`；0700 父目录让两者都不可达（spec 只把 `hub-upgrade/` 写成 0755，未处理更外层的 0700）。裁定：`/var/lib/meshmux-installer` 改 `0711`（可穿越、不可列举），`hub-upgrade/`、`upgrade/` 各 0755，`results/` 0750 `root:meshmux`；两个 ledger 仍 0600 root，`local-line/` 仍 0700，因此 Web 能读 result 与 manifest、不能列目录、不能读 ledger。Task 4 用 R-SURFACE 测试钉住这三件事。
2. **Web 单元没有请求目录写权**。`meshmux-web.service` 是 `ProtectSystem=strict` + 空 `CapabilityBoundingSet=`（`internal/install/render.go:130-152`），`/run/meshmux-hub/requests` 默认不可写；spec §5.1/§5.9 假定 Web 写它但未改 web 单元。裁定：渲染时追加 `ReadWritePaths=/run/meshmux-hub/requests`（Task 4），并在单元测试与 `scripts/ci-hub-components.sh` 中验证。
3. **§5.2 步骤 7 的“旧代保留到新代 confirmed 后的下一次 GC（keep=1）”在 C1 的扁平单槽布局里不可表达**。C1 把 Hub 记录钉死为 `<data-dir>/database-backup/record.json` + `payload/` 且只保留一代、拒绝 `<op32hex>/` 语义；这个单槽没有第二个位置存放“上一代”，新 backup 发布 staged 记录时必然替换旧的。裁定：**Hub 的 flat 记录由新 backup 原子替换**；B8 在 Hub 上退化为“失败或未确认时绝不删除当前记录与载荷”（`TestBackupOrderVacuumIntegrityRecord`、`TestSingleDBIntegrityFailureKeepsOldGeneration`），`backup.GC(LayoutFlat, keep>=1)` 恒为 no-op（`TestGCFlatKeepsOneGeneration`），§5.2 的“keep=1 回收”只在 per-op 布局（Node）上成立。功能上不丢回退源：升级 N+1 的备份记录本身就是 N+1 前的完整 DB 状态，即 Hub 侧的 N-1 等价物。

**另一处非缺口的设计决定（记录在此以免执行者自行发明）**：§5.2 回执 `status=restoring` 但 §5.5 状态机没有 `restoring`，且 `HUB_UPGRADE_BUSY` 只挡 `backup`；两个并发 restore 会各写请求。裁定：restore 要求 journal `∈ {failed, partial, verifying}`、**不存在**任何请求文件、journal 不是 `queued|applying|restarting`，否则 `HUB_HANDOFF_BUSY`/`HUB_UPGRADE_BUSY` 零写；journal 不新增状态（保持 spec 冻结集合），restore 期间事实由请求文件 + result 表达（Task 7）。
